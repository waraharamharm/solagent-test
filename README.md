# SolAgent

Приложение, которое превращает «арендовал VDS» в «работает мой собственный сервер связи» (Flexisip) с телефона, без знания Linux. Подключается к серверу пользователя по SSH, запускает установку на самом сервере, показывает ход работы. Если шаг упал, ИИ (со своим API-ключом пользователя) читает очищенный лог и предлагает одну команду исправления. Команда выполняется только после подтверждения.

Репозиторий приватный, это тестовая сборка для двух разработчиков. Состояние на 27.10.2026: этапы 1–8 готовы, этапы 9–11 впереди (см. [Статус](#статус-и-план)).

Состав репозитория:

| Часть | Папка | Что это |
|---|---|---|
| Приложение | `lib/`, `android/`, `windows/`, `test/` | Flutter: Android (основная цель) и Windows для разработки |
| RAG-сервер | `rag_server/` | Python/FastAPI: поиск по знаниям и очередь решений |
| Релизы | `releases/`, [GitHub Releases](../../releases) | Собранные APK |

## Принципы

1. Ничего не запускается на сервере пользователя, пока он не увидел команду и не подтвердил её.
2. Секреты (пароль или ключ сервера, ключ ИИ, ключ RAG) лежат только в защищённом хранилище телефона.
3. Всё, что уходит наружу (ИИ, RAG, журнал на сервере), сначала очищается от IP, хостов, логинов, токенов, паролей и ключей.
4. Всё, что приходит снаружи (лог, знания из RAG, журнал с сервера), для ИИ недоверенные данные, а не инструкции.
5. Ошибки показываются понятной фразой на языке интерфейса. Технический текст (код, статус, сообщение сервера) остаётся рядом.

## Как устроено приложение

    fix/          очистка лога, политика команд, советник ИИ, цикл починки

### Развёртывание на сервере (этап 1)

Задача запускается на самом сервере отдельным процессом (`setsid nohup`), в каталоге `~/.solagent/jobs/<id>/`. Обрыв SSH её не убивает. Прогресс читается по номеру строки лога. Состояния: `running`, `finished`, `cancelled`, `lost`, `unknown`. После перезагрузки сервера задача считается `lost`.

### Цикл самоисправления (этап 3)

1. Запуск скрипта.
2. Код выхода не 0 → лог очищается (`LogRedactor`) → ИИ получает его как недоверенные данные и отвечает JSON: диагноз, одна команда, пояснение.
3. `CommandPolicy` проверяет команду: запрещённые не показываются (ИИ получает отказ), опасные идут с предупреждением.
4. Пользователь подтверждает или отклоняет. Подтверждённая команда выполняется ровно в том виде, в каком показана (`set -e`, задача `<id>-fN`).
5. Исходный скрипт запускается повторно (`<id>-rN`). Не больше 3 раундов.

### ИИ

Пользователь приносит свой ключ. Пресеты: DeepSeek, Grok, OpenRouter, OpenAI, свой OpenAI-совместимый адрес. Адрес должен быть `https`. Ключ хранится в `SecureStore` и нигде не показывается после сохранения. Из России OpenRouter без VPN может отвечать 403. Ошибки 401 и 403 различаются в интерфейсе.

### База знаний в промпте (этап 8)

- Запрос в RAG строится из последних 15 строк лога (не более 1500 символов), очищается на телефоне и идёт с тегом ОС (например `ubuntu-24.04`).
- Найденные фрагменты добавляются в промпт блоком `<knowledge>`, журнал блоком `<history>`. Оба блока описаны в системном промпте как недоверенные данные. Закрывающие теги в содержимом нейтрализуются.
- Документация в `<knowledge>` не очищается повторно, чтобы примеры IP из документов не терялись.
- Любая ошибка RAG или журнала не останавливает починку.

## Безопасность

- **Секреты на телефоне.** `flutter_secure_storage`: пароль и ключ сервера, ключ ИИ, ключ RAG.
- **Вход.** Экраны сервера, развёртывания и подтверждения команд закрыты биометрией или PIN устройства (`local_auth`). Без блокировки экрана доступ закрыт. При уходе в фон блокировка возвращается.
- **Сервер.** Отпечаток хоста запоминается при первом подключении (TOFU) и проверяется дальше. Чужой отпечаток отклоняется.
- **Очистка (`LogRedactor`).** IP, имя хоста, логин, домашние пути, токены, пароли в `key=value`, флаги CLI, URL с логинами, ключи (PEM, `AKIA…`, `AIza…`, `xox…`), e-mail. Работает в изоляте.
- **Политика команд.** Запрещены разрушительные команды, остальные идут с предупреждением. Решение всегда за пользователем.
- **Недоверенные данные.** Лог, знания и журнал помечены в промпте как данные. Правки журнала на сервере не дают команд ИИ.
- **Ошибки.** Единый тип `AppProblem` (текст на языке интерфейса + технические детали), `RagFailure` и `LlmFailure` локализуются на границе интерфейса.
- **Публикация.** В коде нет ключей, паролей и адресов серверов. Сервис знаний хранит только очищенные тексты.

## RAG-сервер

`rag_server/`, пакет `solrag`: Python 3.12, FastAPI, SQLite (WAL) + `sqlite-vec` + FTS5, эмбеддинги `fastembed` (модель `multilingual-e5-small`, ONNX). RAG = поиск + хранение, своего LLM у сервера нет.

### Поиск

Гибридный: BM25 (FTS5) + векторный (KNN), слияние RRF. Фильтр по ОС внутри KNN: `ubuntu-24.04` видит записи для `ubuntu-24.04`, `ubuntu` и общие. Порога релевантности нет, поиск всегда отдаёт ближайшее.

### API

Все ответы с ошибками одного формата, `message` по-английски и без эха входных данных:

```json
{"status": 401, "code": "unauthorized", "message": "Missing or invalid API key"}
```

| Метод и путь | Назначение |
|---|---|
| `GET /v1/health` | `{"status":"ok"}`, без ключа |
| `POST /v1/search` | `{query ≤ 4000, os?, k ≤ 20}` → `results` |
| `GET /v1/bundle`, `GET /v1/bundle/archive/{sha256}` | манифест и неизменяемый архив базы (клиент пока не использует) |
| `POST /v1/solutions` | решение от клиента → `202 pending`, в поиск не попадает до модерации |

### Авторизация и лимиты

- Ключ `Authorization: Bearer sol_…`. В базе хранится только sha256.
- Выдача и отзыв на сервере: `python -m solrag.admin key-create --label X`, `key-list`, `key-revoke ID`.
- Лимиты (в памяти, один воркер): поиск 30 в минуту, решения 10 в час, бандл 30 в час на ключ; 10 неудачных авторизаций в минуту на IP; ответ `429` с `Retry-After`. Тело запроса не больше 32 КБ (`413`). В очереди модерации не больше 20 решений на ключ. Лимиты не переживают рестарт.
- Решения очищаются скраббером при приёме. Если секрет остался, ответ `422 secrets_detected`.

### Модерация

Только через CLI на сервере, HTTP-админки нет: `pending`, `show ID`, `approve ID` (повторная проверка на утечки, потом попадает в поиск), `reject ID`, `withdraw ID`.

### Индексация и очистка знаний (этап 5)

`solrag/scrub.py` вычищает пароли, токены, PEM, ssh-логины, MD5, `IDENTIFIED BY`, IP (заменяются на адреса из TEST-NET), домашние пути, e-mail и локальные литералы из `rag_server/data/scrub_literals.json` (файл не в git). `solrag/indexer.py` работает по белому списку корней. Сначала всё чистится и проверяется, при любой утечке сборка отказывает до записи. Пересборка идемпотентна.

```powershell
cd rag_server
.\.venv\Scripts\python -m solrag.indexer --src data\source\xmobile-flexisip --out data\knowledge-out --literals data\scrub_literals.json
```

Результат на 27.10: 89 файлов, 345 кусков, независимая проверка (`data/verify.py`, значения берутся из сырого исходника) нашла 0 утечек. Очищенная копия залита одним коммитом, без истории, в `waraharamharm/solagent-knowledge`. Исходник — чужой приватный репозиторий с настоящими секретами, поэтому копия идёт отдельно и в этот репозиторий не входит. Скрипты в знаниях обезличены, но под произвольный VDS ещё не параметризованы.

## Журнал на сервере пользователя

Чтобы в новом сеансе ИИ знал, что уже делали, а не анализировал сервер с нуля, приложение ведёт журнал на сервере: `~/.solagent/journal.jsonl`.

- Одна JSON-строка на событие: время, вид, задача, краткое описание, подробности. Виды: запуск и конец деплоя, диагноз, предложенное исправление, решение пользователя, запуск и результат исправления, итог прогона.
- Всё проходит через `LogRedactor` до записи. Описание до 300 символов, подробности до 1500.
- Права: файл `600`, папка `700`. При 1 МиБ файл уходит в `journal.jsonl.1`.
- В начале сеанса читаются последние записи (хвост до ~200 КБ) и передаются ИИ в блоке `<history>` (не больше 20 записей и 6000 символов). Строки с ошибками разбора пропускаются.
- Сбой записи или чтения никогда не останавливает починку.

## Продакшен RAG: развёртывание

RAG работает на `https://rag.mtoper.ru` (VDS, пользователь без sudo).

- Каталог `~/solrag/{app,venv,data}`. Пересборка базы на сервере не делается: копируются готовые `rag.sqlite3`, бандл и модель.
- Сервис `solrag.service` (systemd `--user`, `127.0.0.1:8795`, `MemoryMax` 1500 МБ, `linger` включён).
- nginx: отдельный сайт `sites-enabled/solrag` (другие сайты на сервере не затрагиваются), TLS от certbot (автопродление), лимит тела 64 КБ, 10 запросов в секунду на IP, ответы 413/429/503 от nginx тоже в JSON.
- Файлы для root: `rag_server/deploy/` (`solrag.service`, `nginx-solrag.conf`, `root-setup.sh`). Повторный запуск `DOMAIN=… bash root-setup.sh` безопасен.

Обновление кода: архив `solrag` + `pyproject.toml` → `scp` → `pip install ./app` в venv → `systemctl --user restart solrag`.

Выдача ключа клиенту (на сервере):

```bash
SOLRAG_DATA_DIR=~/solrag/data ~/solrag/venv/bin/python -m solrag.admin key-create --label имя
```

Ключ показывается один раз. В приложении он вводится на вкладке «ИИ» → «База знаний».

## Ловушки и решения

- **Тесты Flutter на Windows иногда падают с «did not complete» или «Connection closed before test suite loaded»** на случайном файле. Поодиночке файлы проходят. Помогает остановка демонов Gradle и Java и запуск `flutter test -j 1`.
- **Меню с `null`-значением не вызывает `onSelected`.** Для пункта «как на устройстве» используется значение `''`.
- **`kotlin.incremental=false`** в `android/gradle.properties`: кэш pub на `C:`, проект на `D:`, иначе сборка падает.
- **PowerShell и кириллица.** `Set-Content` без `-Encoding` портит русский текст в файлах. Редактировать через инструменты редактора или `WriteAllText` в UTF-8.
- **nginx 1.24** не знает директиву `http2 on;`.
- **Цепочечные тела запросов** и лимит: `BodyLimitMiddleware` отвечает 413 вместо 400 от фреймворка.
- **PowerShell и `\n` в строках Dart.** Не вставлять управляющие символы через шелл-замены. Править через редактор.
